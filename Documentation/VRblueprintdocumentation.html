Initial Level and Shader Caching

Due to the hardware constraints of Quest 2 and Quest 3, developers are provided with an overall memory pool of 8 GB. However, it is crucial to keep in mind that this is unified memory shared directly between the mobile GPU chip and system RAM.

When a user installs the application from an APK file for the first time, cached shaders are completely absent. As a result, upon entering a location, the user will experience frequent frame drops. This occurs because geometry and shaders are being compiled on the fly for everything entering the camera's view, leading to severe VRAM overhead and heavy CPU load.

To avoid this negative user experience, there are two potential approaches:

  1. Manual File Transfer: Pre-generating cached shader files on a separate headset prior to deployment, then providing these files along with instructions on which device directory the user needs to manually copy them into. This workflow is cumbersome and unintuitive.
  2. Automated In-Game Warmup (Selected Approach): During initial level loading/initialization, the user is seamlessly teleported across a series of predefined camera points throughout the map without realizing it. The camera pauses at each point for a few seconds to give the hardware enough time to process and cache everything in view before moving to the next position. Once the caching pass is complete, the player is dropped back into the main HMD start point with the fully rendered level. This approach is much more predictable, robust, and completely frictionless for the end user.

Main Level & Shader Warmup System

When the user loads into the main level, notice the key warmup actors placed in the scene: BP_WarmupCamera, BP_WarmupManager, BP_WarmupSphere, and the Level Blueprint.

Here is a step-by-step breakdown of how the process works:

  1. Level Blueprint: Re-enables the VR components that were disabled on the initial menu level (specifically activating the measurement menu on the left hand). It also enables the WidgetLoading component residing inside VRPawn. Next, it temporarily disables player movement by setting MovementSpeed to 0 via a Cast To VRPawn node. Movement is restored after a 10-second delay.
  2. BP_WarmupSphere: This blueprint actor is positioned at the player's initial spawn coordinates. It contains no internal Blueprint logic. Its sole purpose is to wrap the player in total darkness upon loading, obscuring the main environment. This sphere is destroyed at the end of the warmup sequence once the HMD view is restored.
  3. BP_WarmupManager: This is the core controller governing early-boot behavior. Upon level initialization, it re-enables WidgetLoading inside VRPawn and caches references to BP_WarmupSphere for later cleanup.
  4. Target Points & Frustum Culling Bypass: All TargetPoint actors placed manually throughout the level are added into an array. These points define the precise locations where the camera will teleport to process the scene.
  • Teleportation between points is managed through BP_WarmupCamera to maintain a seamless black transition for the user.
  • To prevent the user from assuming the application has frozen, a fake progress/loading bar is rendered inside the UI.
  • Crucial Detail: To prevent Unreal Engine's frustum culling from culling geometry and skipping shader compilation behind the sphere, the material applied to BP_WarmupSphere uses a near-opaque blend mode with an Opacity value of 0.999. Because it is technically translucent (not 100% opaque), the engine's renderer evaluates and caches all environment geometry and shaders visible behind the sphere. While this causes temporary frame drops during the warmup phase, it ensures that everything is fully cached before gameplay begins.
  1. Warmup Finalization (Warmup_Finish): Once the array of target points reaches its maximum index, execution loops back to index 0. Passing the >= 0 check triggers the final Warmup_Finish event: temporary warmup actors and blueprints are destroyed, and the active camera view snaps cleanly back to the player's primary spawn position.

Mirror Systems

Due to mobile hardware constraints, two distinct methods are used to simulate real-time mirrors:

Method 1: Cubemap Reflection (Static / Performance-Focused)

This simple, low-cost method utilizes a SceneCaptureCube placed within the scene. The generated cube texture is assigned to a specialized material that allows dynamic scaling of the cubemap's height, depth, and width bounds. However, this approach is an approximation: extreme scaling values will introduce noticeable distortion into the reflected texture.

Method 2: Dynamic 2D Capture with Distance Culling & Parallax Distortion (BP_MirrorBathroom_01)

A more complex and scalable method using a SceneCaptureComponent2D to capture the scene every few frames and pass the resulting render target to the mirror material. To optimize performance:

  • Proximity Activation: Frame capture runs only when the player enters the mirror's detection zone; distant players cause the SceneCapture component to pause rendering entirely.
  • Parallax / View-Dependent Positioning: Because a SceneCapture component does not naturally adjust its perspective relative to the user's headset position, a custom math function calculates the offset between the player's vector and the component, dynamically shifting the capture camera position to mimic realistic head-tracked reflections.

A fully working reference implementation can be found in BP_MirrorBathroom_01

Method 3: Dynamic Texture Resolution Scaling (BP_MirrorBathroom_02)

In BP_MirrorBathroom_02, the dynamic capture logic is further expanded. Because this specific mirror is located in a long hallway visible from a far distance, standard full-resolution capture at range would waste GPU resources. To optimize this, the blueprint dynamically scales down the render target's capture resolution based on the player's distance from the actor.
